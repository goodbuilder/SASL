1. 핵심 설명

StereoCAM은 두 대의 고정 카메라가 가상 드론을 보는 실험용 시뮬레이션입니다. 이 작업은 영상과 시뮬레이터가 만든 위치 관측을 사용해 카메라 방향을 추정하고, 미리 정한 시험 비행에서 드론 위치 계산을 평가합니다.

들어오는 것39개 실행 조건, 가상 카메라·드론 모델, 비행 경로, 지정 오차를 넣은 모의 센서 관측.
실행 중 일어나는 것가상 비행을 한 번에 하나씩 준비하고, 좌우 원본 영상과 촬영 시각·시뮬레이터 참 위치를 저장합니다.
나오는 것원본 영상 저장 파일, 프레임 연결과 객체 탐지 결과, 품질 판정, 별도 분석으로 얻은 카메라 방향 추정과 위치 평가.
무엇을 증명하나정해진 가상 조건에서의 동작입니다. 실제 카메라나 기체의 성능을 직접 입증하지 않습니다.
용어: G0는 카메라 명목 방향 그룹, G1은 좌우 방향을 각각 0.5°씩 반대로 기울인 그룹입니다. P0–P4는 카메라 교정에 쓰는 개발 경로, V0는 결과를 미리 보지 않도록 남겨 둔 최종 평가 경로입니다. RTK는 위치 측정 방식의 이름이며, 여기서는 실제 RTK 장비가 아니라 정해진 오차를 넣은 시뮬레이터 생성 위치 관측을 뜻합니다.
이해를 위한 한 문장: “가상 비행을 기록하고, 각 영상이 언제 어디서 촬영됐는지 맞춘 다음, 카메라 방향 추정법을 비교하고, 미리 잠가 둔 별도 비행으로 위치 성능을 평가한다.”
코드 구현 소스에 동작이 있음검증됨 지정한 로그·시험이 확인됨진행 중 현재 상태가 바뀌는 작업계획·미완료 아직 증거가 없음

3. 한 번의 실행은 이렇게 진행됩니다

전방거리 400m · 횡이동 0m · 고도 146m

실제 v1.2 캠페인에서는 실행기가 가상 장면과 가상 기체를 준비하고, 녹화 준비가 확인된 뒤 전용 비행 제어기가 경로를 수행합니다. 비행 제어와 영상 속 드론 탐지는 분리되어 있습니다. 좌우 원본 영상을 먼저 무손실로 저장한 다음, 비행이 끝난 뒤 탐지와 참 위치 정합을 계산합니다.

현재 기본 버튼/명령의 의미: 저장소의 기본 설정은 xlsx_plan입니다. 이 모드는 39개 실행을 계획하고 검사할 뿐 Gazebo를 띄워 비행하지 않습니다. 실제 전체 실행은 별도 캠페인 설정의 xlsx_all처럼 실행 모드를 지정해야 합니다. 보고서 작성 시점의 설정을 다시 읽고, 오래된 예시 명령을 현재 동작으로 소개하지 않아야 합니다.

한 번의 “실행 슬롯”은 manifest의 조건 하나입니다. 녹화가 끊겨 다시 하더라도 이전 파일을 덮지 않고 같은 run_id 아래 새 attempt로 남깁니다. 반대로 탐지율이 낮거나 교정이 비수렴했다고 더 좋은 결과가 나올 때까지 재실행하지 않습니다.

5. 교정과 최종 평가에서 비교하는 것

기록을 모은 다음에는 각 trial에서 카메라의 XYZ 위치는 합성 RTK 관측 좌표에 고정하고, 좌우 카메라의 방향을 추정합니다. 카메라 IMU의 roll/pitch 측정에는 불확실성이 있으므로 주 방법은 이를 유한한 참고값으로 쓰며 참 방향에 강제로 고정하지 않습니다.

방법쉽게 말하면드론 위치 정보
A 독립 교정왼쪽·오른쪽 카메라를 각각 영상과 위치 관측에 맞춤같은 모의 RTK를 활용
B 공동 교정두 카메라가 같은 숨은 드론 위치를 공유하도록 함께 맞춤A와 같은 모의 RTK 및 불확실성 사용
C 스테레오만좌우 영상 기하로 방향을 맞춤드론 RTK·GT 정답·명령 경로를 입력으로 주지 않음
RPY_IMU · 주 방법각 카메라 roll, pitch 보정, yaw를 모두 추정합니다. 좌우 카메라 roll·pitch·yaw를 모두 계산합니다. IMU roll/pitch 관측은 유한한 불확실성을 가진 참고값입니다.
YAW_ONLY · 비교 기준yaw만 추정합니다. roll/pitch는 RPY_IMU와 같은 IMU 측정값에 고정합니다. 좌우 카메라 yaw만 계산합니다.

모의 센서 관측을 바꾸어 수행하는 Monte Carlo 100회는 39회와 별도의 추가 비행이 아닙니다. 기존 비행 기록을 재사용해 알고리즘 계산을 반복합니다. 각 반복의 난수 설정이 실제로 어느 모듈에 적용됐는지 확인해야 하므로, seed 숫자만 다르다고 통계적 독립성이 입증되는 것은 아닙니다.

동적 현황의 증거 시점: 캠페인 run_status/qc_summary 파일은 2026-10-18 05:00 KST 수정 시각을 보이며, 분석 로그와 자원 감시는 2026-10-18 16:00 KST에도 실행 프로세스가 RUNNING임을 보여줍니다. trial 출력은 제출 로그와 완료 수를 구별했습니다. 이 표를 외부 보고에 재사용할 때는 그 시점의 상태 파일과 완료 marker를 다시 읽어 날짜·시간을 갱신해야 합니다.

다섯 가지 과장 방지

  • 저장소의 기본 캠페인 명령은 현재 xlsx_plan일 수 있으며, 기본값만 실행했다고 비행이 시작된 것은 아닙니다.
  • 이 캠페인의 YOLO는 기록 후 처리되므로 비행 중 실시간 inference latency를 증명하지 않습니다.
  • 파일 checksum은 저장 이후 파일이 바뀌지 않았음을 보여주며 시뮬레이션의 현실성을 입증하지 않습니다.
  • QC의 “유효”는 기록·규격 검사 판정이지 좋은 위치 정확도나 높은 탐지율이 아닙니다.
  • PX4의 LAND/ON_GROUND 표시와 실행 종료는 물리적인 접지 여부의 독립 증명이 아닙니다.
부서장 권고: 원본 수집과 오프라인 추정기 완료를 별도 KPI로 보고합니다. 먼저 전체 분석 완료 marker와 read-only 결과 감사를 확인한 뒤에만 교정 정확도나 V0 결과를 결론에 씁니다.
