MC100은 100회 비행이 아니다

MC100은 기존 39개 실행 기록에 모의 센서오차 표본을 적용해 오프라인으로 다시 계산하는 절차다. 100 trial이 각기 여러 조건을 포함하므로, 실제 분석량은 100보다 훨씬 크다.

100MC trial · 번호 000–099
39 → 31 + 8run 기록 → 교정 + 잠긴 V0 평가
424primary case ID / trial
42,400전체 primary case ID
요약: 한 trial은 25개 G0 교정 슬롯과 6개 G1 교정 슬롯에서 yaw 초기값과 표본 범위를 조합한다. 8개 V0는 교정에서 제외하고 freeze 뒤에 평가한다.
읽는 법예제 조건기초 개념분석 순서끝까지 계산검산과 상태좌표 계약

이 페이지에서 다시 계산할 것

목표

계산기로 한 trial의 case 수를 구하고, 100 trial의 전체 수를 손으로 재현한다. 그 뒤 각 결과가 어떤 방법·입력·표본 범위에 속하는지 구분한다.

필요한 도구

곱셈과 덧셈이 가능한 계산기면 충분하다. 이 예제의 known answer는 solver의 위치추정치가 아니라 analyzer의 교정 case ID 개수다.

실험 해석

이 수치는 모의 관측을 만드는 설계값이다. 장비 측정 결과나 현장 성능 보증이 아니다.

카메라 광학 중심은 측정 RTK 위치에 고정한다. 카메라 위치를 solver가 교정하지 않는다.

0.1

trial은 비행 한 번이 아니다

무엇인가

Monte Carlo trial은 모의 측정오차 한 벌을 뜻한다. 같은 원본 촬영을 두고 trial마다 합성 센서 관측을 만들어 교정 결과의 변동을 본다.

왜 필요한가

“100회”를 물리 비행 100회로 읽으면 데이터 수집량을 잘못 계산한다. MC 횟수는 오프라인 반복 수다.

예제의 숫자로

trial index t=0,…,99가 있다. v1.2 규격은 원본 manifest 39개를 정의하며, MC 반복마다 새 Gazebo 비행을 뜻하지 않는다.

직접 확인

trial 007은 새 비행인가?

아니다. 같은 source run을 trial 007의 합성 오차로 다시 처리한다.

0.2

case ID는 run·trial·yaw·범위를 묶는다

무엇인가

한 교정 case identity는 (run_id, trial_index, yaw_case, data_scope) 조합이다. A/B/C와 자세 variant의 각 solver 결과는 case 안에 들어간다.

왜 필요한가

42,400은 비행 수나 solver 결과 행 수가 아니다. 서로 다른 조건을 구별하는 case ID 수다.

예제의 숫자로

G0: 25 × 8 yaw × 2 scope = 400 cases/trial
G1: 6 × 2 yaw × 2 scope = 24 cases/trial
400 + 24 = 424 cases/trial; 424 × 100 = 42,400 case ID

직접 확인

G1 한 슬롯은 한 trial에서 몇 case인가?

G1에는 primary zero와 GPS_YAW90 두 yaw 경우, 두 scope가 있다. 1×2×2=4 case다.

0.3

같은 trial 입력으로 방법을 짝비교한다

무엇인가

짝비교는 두 보정 방법에 같은 trial의 영상·카메라 RTK·카메라 IMU와 초기 자세를 주는 방식이다. A/B에는 같은 드론 RTK 관측을 쓴다.

왜 필요한가

입력이 달라지면 결과 차이가 보정법 때문인지 오차 표본 때문인지 분리하기 어렵다. 동일 표본 비교는 그 혼동을 줄인다.

예제의 방법으로

RPY_IMU는 카메라 roll/pitch/yaw를 추정한다. YAW_ONLY는 같은 카메라 IMU roll/pitch 측정값을 고정하고 yaw만 추정한다. C는 드론 RTK가 없다.

직접 확인

C에도 드론 RTK가 들어가나?

아니다. C_no_drone_rtk_joint는 drone RTK를 solver에 주지 않는다. camera RTK는 유지한다.

기호

0.4

위치 frame과 카메라 자세 frame을 분리한다

무엇인가

frame은 벡터의 축 순서·방향·원점을 정한다. 이름 없는 세 숫자를 다른 frame의 세 숫자와 바꿔 읽을 수 없다.

왜 필요한가

MC100은 RTK 위치오차와 optical 자세오차를 함께 분석한다. frame을 바꾸어 읽으면 같은 오차값도 다른 방향과 위치를 뜻한다.

예제의 frame으로

세계 위치는 ENU [east,north,up]이며 project spec에서 [x,y,z]=[E,N,U]라고 선언한다. 따라서 RTK 표준편차 σ_ENU=(0.02,0.02,0.04) m의 두 번째 성분은 north다.

변환 계약: world ENU (x,y,z)=(E,N,U)에서 원점을 확인하고 축 정렬한 경우 PX4 local NED 위치는 [N−N0, E−E0, U0−U]다. public baseline frame은 [F,R,D]=[y,x,0.1−z]다. 각 변환은 해당 origin과 rig 계약을 함께 기록한다.

직접 확인

σ_ENU의 세 번째 값은 optical z인가?

아니다. 여기서는 world ENU의 up 축이다. Optical RDF의 세 번째 축은 forward다.

1. 분석은 어떤 순서로 돌아가나?

입력 QC와 표본 생성을 먼저 하고, 방법 비교를 마친 뒤 경로를 freeze한다. V0 최종평가는 freeze 뒤에만 한다.

단계작업완료 증거
1 · 입력 QCrun/attempt identity, 파일, frame, seed, 원본 checksum을 확인한다.기대 39 slots와 원본 manifest가 맞는다.
2 · MC draw각 trial에서 camera IMU/RTK와 필요한 synthetic observation을 만든다.trial 번호와 shared input identity를 기록한다.
3 · 교정31 calibration slots에 424 cases/trial을 처리하고 A/B/C × RPY_IMU/YAW_ONLY 결과를 저장한다.case 누락·중복, 실패·미수렴, frame을 보존한다.
4 · freezeG0 calibration 근거로 경로와 설정을 고정한다.freeze가 V0 위치오차 접근보다 먼저 생성된다.
5–6 · V0와 감사8개 final-evaluation slots로 평가하고 summary, report, hash를 검증한다.평가 입력, truth 경계, 결과 범위와 provenance를 독립 확인한다.

3. 손계산과 코드·저장 기록 대조

검산결과무엇을 확인하나
손계산25×8×2 + 6×2×2 = 424; 424×100 = 42,400실제 manifest 그룹 수, yaw 경우 수, scope 수.
analyzer case enumerationtrial마다 424, 100회에서 42,400개의 고유 case key_calibrate_run_trial를 실제 v1.2 manifest/spec로 호출. Fit/I/O용 _calibrate_scope와 checksum 함수만 stub 처리.
저장된 진행 censustrial 000–002 각 424/424; trial 003–004는 당시 진행 중; 총 1,688 case identities 관측중간 파일 identity 확인. 전체 byte audit, 수치 fit 검증, V0 최종 보고 완료 증거는 아니다.

손계산과 analyzer enumeration은 0 case 차이다. 이 코드 확인은 case 생성 순서와 조합 수만 검산했다. optimizer, 실제 output hash, V0 평가를 재실행하지 않았다. system Python에서 SciPy/NumPy 호환 경고가 출력돼 수치 solver 검증으로 확대 해석할 수 없다.

역사적 진행 상태 · 2026-10-18: 저장된 verification 기록은 full MC가 진행 중이던 snapshot이다. 당시 PID와 진행 census는 그 시점의 상태를 보여주며 이후 완료 상태를 나타내지 않는다.
현재 동결 결과: analysis_9cfd7c6cd10b의 primary 42,400 case IDs는 기존 v1.2 yaw 36,200건과 GPS_YAW90 확장 6,200건으로 나뉜다. 민감도 50,000건은 별도 범위다. V0별 MC 결과와 QC·실행별 해석 보완은 보고용 보완 workbook에서 확인한다.

이전 v1.1 결과

당시 실제 자료 분석은 6,822 calibration results, 6,732 V0 rows, 50 sensitivity cases, 36,071 checksums를 기록했다.

뒤이은 범위 감사가 전체 MC scope의 미포함을 확인했다. 이 수치는 과거 실행 기록이지 v1.2 전체 매트릭스 완료 증거가 아니다.

완료 판정

RMSE 숫자 하나가 합격 기준은 아니다. 예상 case coverage, shared inputs, 좌표 변환, truth 차단, freeze 시각, 실패·누락 보존, checksums와 최종 보고를 확인한다.

유효 stereo pair가 200개보다 적으면 MATCHED_200_UNMET로 남긴다. 프레임을 복제하지 않는다.

4. 흔한 오해와 셀프체크

  • “MC100은 비행 100회” — 아니다. 기존 run 기록을 100 trial에서 다시 분석한다.
  • “42,400은 solver 행 수” — 아니다. case identity 수다. main fit은 case당 6개, 총 254,400으로 별도 기록된다.
  • “GPS_YAW90이 참 yaw를 제공” — 아니다. camera RTK baseline으로 만든 초기값이며 참 자세 제약이 아니다.
  • “카메라 IMU는 기체 IMU” — 아니다. 카메라 장착 IMU의 optical roll/pitch 관측이다.
  • “world ENU의 U와 optical RDF의 F가 같은 축” — 아니다. U는 world up, F는 optical forward다.
  • “200 pair가 모자라면 프레임 복제” — 아니다. 미달 상태와 실제 pair 수를 기록한다.
  • “합성 sigma는 장비 정확도 보증” — 아니다. simulation experiment design value다.
  • “V0로 최적 경로를 고름” — 아니다. V0는 freeze 뒤 final evaluation에만 쓴다.
